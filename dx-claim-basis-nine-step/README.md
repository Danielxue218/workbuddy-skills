# dx-claim-basis-nine-step · 请求权基础 · 要件审判九步法（律师版）

> 面向**已接案律师**的给付之诉**判决前冷推演引擎**。站在原告或被告立场，借法官的裁判逻辑，
> 推演一个案子**能不能赢、赢在哪、输在哪、最坏到什么程度**。
>
> 它交给律师的是**代理立场下的研判**，不是中立裁断，**不是判决模拟器**。

---

## 一、这是什么

本 skill 坐在**请求权基础**（Anspruchsgrundlage）方法与 **Rosenberg 规范说**、
**关联分析法**（Relationstechnik）正源之上，把**邹碧华要件审判九步法**转译为律师的对抗性预判工具：
从案由接驳请求权基础、分解要件、按规范说分配证明责任、做两层审查（法律有理性 + 证明前景）、
识别决定性要件、预判对手动作与法官裁判倾向、给出结果区间与最坏情形。

- **场景**：给付之诉（请求为一定给付的诉，约占民事诉讼 99%）。确认之诉 / 形成之诉**出边界、转派**。
- **立场**：原告向 / 被告向**双向**。
- **时态**：前瞻（一审判决前）为主，兼回溯（二审 / 再审的改判 / 发回 / 维持）。
- **材料**：从口述到完整卷宗**分级不拒跑**（L0–L3）。

---

## 二、三条铁律

1. **分级不拒跑** —— 材料不足也先跑出方向，同时标明还缺什么，绝不因材料不全而拒绝研判。
2. **三标出厂** —— 每个结论随带**置信度 + 来源 + 立场方向**，让判断可核、可追溯。
3. **客观与立场物理分离** —— 阶段一至五**只做客观分析、不带立场**；立场打法**只在阶段六**出现。

---

## 三、九步是"体"，六阶段是"用"

**九步是引擎的内部工序（体），不是输出形态。** 律师要的是结论和下一步动作，不是走一遍九步仪式。
所以交付按律师真实办案顺序组织为**六阶段动线**，读序**结论先行**（一页纸摘要 → 六阶段详情 → 附件）。

九步只在两处现形：(a) 方法文件，作为血统；(b) **三张图**，严格对应九步——这是方法自我显现、
推理可被审计之处。

## 六、工作流

1. 加载 `SKILL.md` → 确认场景与边界、装载三条铁律。
2. 按**六阶段动线**推进；每阶段调用 `references/` 下对应文件。
3. 需要出图时，模型只吐 `semantic-map.json`（见 `visual-style-guide.md` §5 三 schema），
   一条命令渲染：
   ```bash
   python scripts/render.py <semantic-map.json> <输出名>
   ```
   产出 `<输出名>.svg`（可编辑）+ `.png`（嵌入 Word 用）+ 审计摘要。
4. 交付**结论先行的律师版报告（Word `.docx`）** —— 用 `scripts/build_report_docx.py` 生成，封面标准深红
   `#991B1B`、三图嵌 PNG、客观/立场硬分隔；如需对客，另出客户摘要（亦为 `.docx`）。

## 七、依赖

- **Python 3**。三个渲染器均为纯确定性布局，**不需要 graphviz**。
- **Word 交付**：`python-docx`（`scripts/build_report_docx.py`）或 docx（npm）；渲染校验用 `soffice`(LibreOffice)。
  **律师交付物是 `.docx`，不是 md。**
- SVG 由渲染器出；PNG 自动探测 `rsvg-convert` / `resvg` / `inkscape` / `cairosvg`，都没有则回落
  `soffice` → PDF → `pdftoppm`；PNG 嵌入 Word 报告。
- PNG 中文需 CJK 字体（如 Noto Sans CJK SC）；SVG 用跨平台字体栈，各系统查看器均可正确显示。

## 八、边界与声明

- **代理立场研判，非中立裁断**；结果**涉及法官自由裁量**，非任何工具所能保证。
