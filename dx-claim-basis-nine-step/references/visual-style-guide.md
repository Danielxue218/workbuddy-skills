# 视觉规范 · 三图样式与语义配色

> 本文件管本项目的**三张图**：要件-证据对照（④⑦）、争议焦点（⑥）、结果预判（⑨）。它规定这三张图**长什么样、
> 什么颜色代表什么、模型要吐什么 JSON**。
>
> **三个立足点先立**：
> 1. **美学风格坐在 `mqc-contract-review` 的视觉标准上** —— 暖调商务色板、扁平、圆角卡片、色块图例。
>    通用样式细则（字号层级、连线箭头、圆角、图例、标题、A4、文字保留可编辑 `<text>`）**一律沿用合同审查
>    `visual-style-guide.md`，本文件不重复**，只写本项目**新增或不同**的部分。
> 2. **引擎照搬 `mqc-litigation-visual`** —— 模型只吐 `semantic-map.json`、绝不碰坐标；确定性脚本包揽全部几何。
>    这套是弱模型也能出稳定专业图的根，原样继承（见 §6）。
> 3. **三图只进律师版，不进客户版**（缪已定）—— 故只管**一档 register**：面向作为分析者的律师，
>    可用法言法语标注，不必降到客户白话档。

## 1. 两个继承，一个本地化

| | 来源 | 本项目怎么用 |
|---|---|---|
| **美学风格** | `mqc-contract-review` 视觉标准（暖调商务） | 沿用其色板、扁平原则、卡片/图例/字号/连线规范 |
| **图形引擎** | `mqc-litigation-visual`（semantic-map → 脚本） | 原样继承：模型吐 JSON、脚本画几何、SVG 主交付 |
| **本地化** | 本文件 | 三张**新布局**的语义配色 + schema（合同审查与诉讼可视化都没有这三种） |

**【规则 · 自足（缪定 A 方案）】** 共享层（`common.py` / `render.py` / `audit.py` / `style-tokens.json`）连同
本项目三个新渲染器一并放入本项目 `scripts/`，**不依赖兄弟 skill 运行时也能跑**（"不接不塌、极度垂直"）。

## 2. 功能色与美学色 —— 两层严格分开（继承合同审查铁律）

**【规则】** 色彩分两层，**同一元素不得混用**（此即 `00-method` §6 反复引用的那条铁律）：
- **功能色**（交通灯）—— **只标状态**：证明前景、置信度、风险档。
- **美学色**（商务扁平）—— **只做呈现**：节点、卡片、区间段、装饰、连线、立场分色。
- **禁止**用美学色标状态（不能用蓝表示"低前景"），也**禁止**用功能色做装饰（不能用交通灯红当节点底色）。

## 3. 本项目色板（暖调锚点 + 单一强调深红）

### 3.1 美学色（呈现层，锚合同审查暖调示例图）

| 角色 | 色值 | 用途 |
|---|---|---|
| **主锚 / 终端** | `#003153` 海军蓝 | 图标题强调、终端/起止节点、主块 |
| 输入 / 判断 / 中性卡 | `#F5F0E1` 米白 | 承载信息的浅卡、判断节点 |
| 次要 / 一方节点 | `#006A4E` 深绿 | 次要节点、被告向节点（见 §4 立场分色） |
| 共同 / 中间态 | `#F6C12C` 双方黄（配深灰字） | 双方 / 共同项、过渡态 |
| 中性文字与线 | 石板灰阶：`#1A1A1A` 标题 · `#606060` 副 · `#A0A0A0` 标签 · `#9CA3AF` 箭头 · `#E0E0E0` 分隔 | 文字层级、连线、分隔 |

### 3.2 美学强调深红（唯一强调，取诉讼可视化标准）

**【规则】** 强调深红 **`#991B1B`**（诉讼可视化标准值），用法：**实心 `#991B1B` 块 + 白字**，无描边、无侧边条、
无浅色调。**每张图至多 1–2 处**，只标全图最要紧的东西（决定性要件 / 最尖焦点 / 最坏情形，见 §4）。
—— 这是全图的视觉焦点，滥用即失效。

### 3.3 功能色（状态层，交通灯，继承合同审查 —— 但**红已弃用**）

| 色值 | 名称 | 标什么状态 |
|---|---|---|
| `#00A650` 正绿 | 高 | 证明前景高 / 置信度高 |
| `#FF9900` 标准橙 | 中 | 前景存疑 / 置信度中 / 待核 |

**【规则 · 红只保留 #991B1B 一种，功能红 #FF0000 彻底弃用】** 交通灯里不再有红。**"低前景 / 最严重"这一档
不另设功能红** —— 它恰恰是决定性要件所在（有争议 × 举证责任在我方 × 前景低），由 §3.2 的强调深红 `#991B1B`
直接承担。故全图**红只有一种**（`#991B1B`），绿橙只标"高 / 中"，其余交给中性灰与深红强调。

**呈现形态**：功能色（绿 / 橙）用**小 `■` 方块（14×14 `<rect>`）+ 语义色**，不做整块填充。

### 3.4 禁用色

沿用合同审查禁用清单（作者品牌深红 `#C00000`、金 `#E8A500`、深绿 `#548235`、indigo、纯黄、荧光绿、渐变等），
**外加**：本项目**不用蓝表示立场以外的语义**；**红只用 `#991B1B`** —— 功能红 `#FF0000` 与合同审查示例的
`#8C1515` / `#C92C2C` 一律弃用（全图仅此一种红）。

## 4. 三图的语义配色映射（本文件的核心）

**【规则】** 引擎的三样产出，各归其色，功能与美学不混：

| 引擎产出 | 色层 | 具体 |
|---|---|---|
| **决定性要件 / 胜负手 / 最尖焦点 / 最坏情形 / 低前景关键项** | 美学强调 | **`#991B1B` 实心块 + 白字**，每图 ≤2 处 |
| **证明前景 / 置信度（高 · 中）** | 功能色 | 交通灯 **`■` 小方块**（高绿 / 中橙）；**低档不另设功能红，归入 `#991B1B` 强调** |
| **立场方向**（原告向 / 被告向 / 中性） | 美学节点色 | 原告向→`#003153` 蓝系 · 被告向→`#006A4E` 深绿 · 中性→`#F5F0E1` 米白 |

*（理据）* 全图**红只有一种**（`#991B1B`）：它既是"哪个是胜负手"的重要性强调，也承接"前景最差 / 最坏情形"这一
最严重状态 —— 因为决定性要件本就是前景最差处，二者天然同指。绿橙功能色只标高中前景；美学节点色标立场读数。
**立场方向只是读数标记，不是打法**——与 `epistemics.md` 立场方向标一致。

## 5. 三张新布局的形态与 schema

> **三图的身份（先立）**：`00-method` §4 定义——**"图是方法自我显现、推理可被审计之处"**。三图不是把教义
> 画好看，是**推理的审计轨迹**：每个元素随带**三标**（置信度 / 来源 / 立场方向，`epistemics.md`）与
> **`【待核验】`** 标签（`claim-basis-table.md`），**真伪不明与证明缺口必须显形**。这是弱模型也能出可信图的根。
>
> **构造纪律（沿《诉讼可视化》四步，蒋勇 / 天同）**：
> 1. **明确对象** —— 三图**只进律师版**（呈团队 / 自研）→ **翔实分析型**，不是呈法官的说服型。
> 2. **选对工具** —— "三言两语用文字，文字不足用表格，表格不足才画图"：图一是**表**、图二是**汇聚关系**、
>    图三是**谱系带**，各司其形。
> 3. **由繁入简，围绕决定性要件 / 焦点精简** —— 与胜负无关的检视项精简、foreground 决定性要件；接**五案型
>    分诊**（只深挖到需要处，多数案子不铺满第二层）。
> 4. **让图自己说理** —— 尤其图三，用不同情形的不同结果让图自证，不靠图外文字。
>
> 模型只吐下列 `semantic-map.json`，**绝不给坐标**；几何由对应 `render_*.py` 确定性生成。举例一律抽象
> （要件 X / 焦点 F），不写具体案由。

### 5.1 图一 · 要件-证据对照矩阵（"逻辑序列主义表"）· `layout: elements_matrix`

**【出处 · 三源合流，不是自创矩阵】** 本图是**吴香香检视表 + 实务"逻辑序列主义表" + 02 两层五站**的合流：
**纵向 = 请求 → 抗辩 → 再抗辩 → 再再抗辩**（实体法适用逻辑）；**横向 = 原被告就每个要件的构成要件攻防**。
这正是吴香香"三层四步"、正源五站、金晶"反对规范三分"的同一张表。

- **形态**：矩阵。**行 = 检视项，按检视顺序纵向分组**：
  - 【成立 · ①积极要件】—— **本项是"要件"，原告举本证**（高度盖然性）
  - 【成立 · ②权利未发生（阻碍）抗辩】·【未消灭 · ③权利已消灭抗辩】·【可行使 · ④权利阻止抗辩（抗辩权）】
    —— **②③④统统是"抗辩"，被告举证**（吴香香："四步里只有成立要件是要件，下面全是抗辩"）
  - 【反抗辩 Replik（复归原告）→ 再抗辩 Duplik（被告）】作迭代子行缩进。
- **列**：检视项 · **攻防方**（原告攻 / 被告防，用立场色）· **规范类型**（主要 / 辅助 / 防御）· **举证责任方** ·
  **证明标准**（本证·高度盖然性 / 反证·真伪不明）· **证明前景** · **争议状态** · **修正因素**（自认 / 书证提出命令 /
  鉴定 / 免证，作前景旁注）。
- **内涵铁律（务必体现，否则又成一张平表）**：
  1. **决定性要件红标 = 三条件同时命中**（有争议 × 客观证明责任在我方 × 现有证据未达标 / 对手能拉回真伪不明），
     `#991B1B` 标该行，并可注明命中了哪三条。
  2. **"无本证不反证"** —— 反证列只在本证未达标时才有意义；检视有依赖顺序，不并列平铺。
  3. **五案型分诊 · 图要表达"在哪一层收官"**：程序站不合法→只画到程序站（预判裁定驳回起诉）；第一层即定论
     （原告主张缺口 / 自曝，或被告抗辩无合理性）→ **不铺证据列**，图止于第一层；只有"双方都有合理性且陈述
     不一致"才铺满第二层证据列。多数案子不进第二层。
  4. **按案型裁行**：物权 / 侵权 / 不当得利**无须审查权利阻碍抗辩**（金晶），该案型不出②的阻碍抗辩行。
  5. 决定性"要件"（原告积极要件）与决定性"抗辩 / 风险"（如时效抗辩权）**分区**，不混行。
  6. **举证责任分层，同一事实两行**（`claim-basis-table.md`）：同一事实在不同层责任方会翻转 —— 如"工程质量"，
     "竣工验收合格"是**积极要件（原告举证）**，"验收后质量缺陷减损"是**权利妨碍抗辩（被告举证）**，
     **须分两行、不得压成一句"质量由谁证"**。
  7. **审计标记随行**：每行带**三标**（置信度 / 来源 / 立场）与 **`【待核验】`**（条号 / 要件未确认者）；
     证明标准的陡增特例（如恶意串通→排除合理怀疑）显性标出。
- **schema**：
```json
{ "layout":"elements_matrix", "title":"…", "stance":"原告向|被告向",
  "收官层":"程序站|第一层|第二层",
  "rows":[
    { "id":"T1", "检视项":"…",
      "步":"①成立积极要件|②未发生抗辩|③已消灭抗辩|④行使抗辩(抗辩权)|反抗辩|再抗辩",
      "攻防方":"原告攻|被告防", "规范类型":"主要|辅助|防御", "责任方":"原告|被告",
      "证明标准":"本证·高度盖然性|反证·真伪不明|排除合理怀疑",
      "前景":"高|存疑|低|待第二层", "争议状态":"无争议|有争议|免证",
      "修正因素":["自认","书证提出命令","鉴定"],
      "决定性":true, "命中":["有争议","责任在我方","未达标"],
      "置信度":"高|中|低", "核验":"✓核验|【待核验】", "子项于":"T0" }
  ] }
```
- **渲染器**：`render_elements_matrix.py`（按"步"纵向分组；`收官层`决定画到哪一层；同组内决定性项置顶；
  `【待核验】`以中性弱化样式标注，不喧宾夺主）。

### 5.2 图二 · 争议焦点汇聚 · `layout: issues_focus`

**【出处 · 坐在邹碧华九步法第⑥步"争点整理"上】** 争点整理是"法官引导诉讼的指挥棒"（邹碧华）。争点分三类：
**实体争点**（法条理解、法律关系性质合同 vs 侵权）·**程序争点**（管辖、当事人主体）·**事实争点**（要件事实真伪）。

- **形态 · 逐焦点汇聚单元**：**一个焦点 = 一个自足单元**——该焦点的三条来源（决定性要件 / 对手主攻线 /
  法官视角）小卡在左，短箭头就近汇入右侧焦点卡；**单元之间无任何跨线**。（旧版三源全堆左、多焦点全堆右、
  彼此多对多连线，线密不可读，已废弃。）来源按流着色（要件 navy / 对手 ink2 / 法官 green），底部三源图例。
  各焦点标其类：实体 / 程序 / 事实。
- **配色**：核心焦点 = `#991B1B` 红卡（唯一强调，白字）；来源卡与汇聚连线走中性美学色（红不外溢到连线）。
  确定性布局，无需 graphviz。
- **schema**（每个焦点自带 feeders，不再用全局 sources / from）：
```json
{ "layout":"issues_focus", "title_text":"…", "stance":"原告向|被告向",
  "foci":[
    { "id":"F1", "label":"…", "类":"实体|程序|事实", "core":true,
      "feeders":[ { "源":"决定性要件|对手主攻线|法官视角", "项":"…" } ] } ] }
```
- **渲染器**：`render_issues_focus.py`（逐焦点垂直堆叠，每单元三来源就近汇入，核心焦点红卡）。

### 5.3 图三 · 结果预判区间带 · `layout: outcome_band`

**【出处 · 坐在邹碧华第⑧步"事实认定"三出路 + 02 程序站上】** 四段结果各有出处，不是随意分段：
- **判决支持诉请** —— 原告就要件事实举证充分（邹碧华 / 吴香香）
- **部分支持** —— 部分要件成立
- **判决驳回诉请（实体）** —— 被告抗辩要件符合，或要件事实**真伪不明→举证责任方（原告）担败诉**
- **裁定驳回起诉（程序）** —— 程序站不合法（`02` §2）；**与"判决驳回诉请"是两种不同结果，须分列**

- **形态**：横向区间带。上述四段结果谱；标出**最可能区间**（强调框）与**最坏情形**。**不是甘特**（无日期轴）。
- **配色**：四段用中性美学色（不整条上交通灯，避免刺眼）；**最可能区间**加美学强调框；**最坏情形**格 =
  `#991B1B`。置信度以功能色 `■` 附在标题旁。
- **内涵铁律**：**最坏情形是叠加推出的**（决定性要件全部失利 + 对手致命抗辩(权)全部成立，`03` §4），
  不是随手指一段；回溯态四段改为**改判 / 发回 / 维持**。
- **schema**：
```json
{ "layout":"outcome_band", "title":"…", "stance":"原告向|被告向", "时态":"前瞻|回溯",
  "segments":["判决支持","部分支持","判决驳回诉请","裁定驳回起诉"],
  "most_likely":"部分支持", "worst_case":"判决驳回诉请",
  "worst_case_由来":"决定性要件全失利+致命抗辩全成立",
  "confidence":"高|中|低", "notes":["关键不确定项…"] }
```
- **渲染器**：`render_outcome_band.py`。

**【规则 · 扩展纪律，继承诉讼可视化】** 加这三张图 = 各加一个兄弟 `render_*.py` + 一个 `layout` 值 +
`validate_map` 分支 + fixtures + `run_checks` 断言，**不动共享层**（`common.py` / `render.py`）。

## 6. 图形引擎（照搬诉讼可视化，原样继承）

**【规则】** 以下机制原样继承，不改：
- **模型只吐 `semantic-map.json`，绝不碰坐标**；确定性脚本包揽全部几何 —— 弱模型也能出稳定专业图的根。
- `render.py` 按 `layout` 字段派生到对应渲染器；`common.py` 管 tokens / 换行 / 字宽 / 校验 / 箭头。
- 需要节点定位时（图二）**用 graphviz 只算坐标、连线全自画**（不信其自动路由）。
- **SVG 主交付**，PNG 靠 `rsvg → resvg → inkscape → cairosvg → soffice` 逐级回落。
- `validate_map` 飞行前校验（缺字段 / 越界 / 悬空引用等）；`audit.py` **数强调深红 ≤2**、抛出待确认项；
  `run_checks.py` 把修过的坑固化成几何 / 美学**不变量断言**。
- **渲染前有人工 checkpoint**（见 §7）。

---

## 7. 保真模型的转变（从"忠于原图"到"忠于分析"）

**【规则】** 诉讼可视化的保真是"逐字忠于**原图**、人工确认转录"。**本项目没有原图** —— 三图从引擎已结构化的
产出（要件清单 / 证明前景 / 结果区间）生成。故保真的**对象变了**：
- 从"图有没有把原图抄对" → 变为"**图有没有忠实呈现引擎的分析、有没有把重点标错**"（决定性要件是不是真的
  那几个、前景档对不对、最坏情形有没有标丢）。
- **checkpoint 仍在**，但确认的是**分析与重点**，不是转录：渲染前把"哪几行标了深红、前景档如何"回给律师核，
  错了改 `semantic-map.json` 重渲，绝不在图里手改坐标。

## 8. 几何与细节铁律（缪定，逐条写死；渲染器必须遵守）

以下七条是**硬约束**，三个渲染器与任何 SVG 输出都必须满足；`run_checks.py` 应尽量把可测的固化成断言。

1. **一切卡片 / 矩形用小圆角** —— `rx` 取 `radius.card`（约 8–12），**不用直角、不用大圆角**。胶囊标签用 `radius.capsule`。
2. **折线的直角拐弯用"非常接近直角的小圆角"** —— 转弯处以小半径圆角过渡（`stroke-linejoin="round"` 或在拐点打一段小圆弧），
   **不留生硬的 90° 尖角**，也不做成大弧线。
3. **所有箭头是等腰三角形，且与线宽配合** —— marker 为等腰三角（`arrow.path`），大小随线宽走（连线 2px 配标准箭头、
   强调 3px 配略大箭头）。
4. **线不许挡住箭头的尖** —— 连线终点**留出间距**（marker `refX` 校准 + 线在到达节点前收尾，约留 4px），
   保证箭头尖角完整外露、不被线覆盖或穿透。
5. **绝对禁止"卡片左侧竖色条"那种 AI 味设计** —— 强调一律用 §3.2 的 `#991B1B` **实心块 + 白字**；
   **不做左边框强调条、不做侧边 accent bar、不做描边高亮**。
6. **连线可用各种灰** —— 主 / 次 / 回路连线在中性灰阶内取不同深浅（`line` / `line_soft` / `note`）；
   **重要连线用标准深红 `#991B1B`**（呼应强调，仍受"每图≤2处红"约束）。
7. **模块内文字要协调、有呼吸感** —— 文字四周留足内边距，行距舒展，标题 / 副文 / 注释分层级；
   卡片不塞满、不贴边，宁可放大卡片也不挤字。

## 9. 本文件不是什么

- **不重复合同审查的通用视觉规范** —— 只写本项目的色板锚点、强调深红、三图语义配色与 schema。
- **不含图形引擎代码** —— 引擎在 `scripts/`（照搬诉讼可视化 + 三个新渲染器）；本文件只定**规范**。
- **不做法律判断** —— 三图画什么由引擎产出决定；本文件只管**怎么画、什么颜色**。
- **不管客户版** —— 三图只进律师版；客户摘要维持纯文字。
- **不含案由专属内容** —— 三布局与举例对全部给付之诉通用。
