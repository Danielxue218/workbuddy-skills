# 01 阶段 · 接案与案情固定

> 本文件是引擎的**前门**，对应六阶段动线的**阶段一**。它做一件事：把律师手里的原始东西 ——
> 上传的起诉状 / 答辩状 / 合同 / 判决书 / 证据清单，或只是一段口述 —— 转成一张**结构化接案卡**，
> 交阶段二（`engine/01`）找法。喂进去的是不是垃圾，这一关定。
>
> **两条纪律先立**：(1) 本文件**不含案由专属字段**，登记的东西对全部给付之诉一视同仁，建设工程只是
> 引擎下游的打样，接案卡对任何案由都同样跑。(2) 本文件**不做法律推理，也不做事实认定** —— 不找请求权
> 基础、不分要件、不判胜负、不判事实真伪、不识争点、不判薄弱点。它只**固定输入**：把该问的问清、
> 该切的切开、该标的旗标好。
>
> **五轴按律师接案动线排**：律师接案的自然次序是"**谁告谁、我代理谁 → 发生了什么、双方各执何词 →
> 他要什么 → 什么案由 → 到哪一步了**"。五轴即依此顺序：**当事人与地位 → 争议事实与双方主张 →
> 诉的请求 → 案由线索 → 时态**。其中**争议事实与双方主张（轴二）是全案的原料**：诉请由事实提炼，
> 引擎第一层的原告站 / 被告站要靠"双方各执之词"才跑得动（`engine/02` §3）。

---

## 0. 位置与产出

- **输入**：律师上传的材料，或律师的口述 / 填写。**允许薄到只有一句话**（分级不拒跑）。
- **产出**：一张**结构化接案卡**（五轴 + 材料成熟度评级 + 缺口旗标 + 边界旗标），交 `engine/01`。
  五轴即 `engine/01`（及经其转交 `engine/02`）的输入约定：**① 当事人与我方地位、② 争议事实与双方主张、
  ③ 诉的请求、④ 案由线索、⑤ 时态**。

---

## 1. 两种录入形态（一套 schema，两种填法）

**【规则】** 接案卡的五轴 schema 只有一套（§3）。它有两种被填满的方式，**律师默认走第一种**：

- **主形态 · 材料上传抽取（默认）** —— 律师上传材料，引擎从中**抽取**五轴各字段，抽不到的标"缺"。
  多数律师要的是"传完等结果"，不是答一长串问题。所以引擎抽取后**只就"缺的最小必要项"回问一次**
  （§2），其余缺口挂旗标、不停机。
- **副形态 · 引导问答 / 可粘贴模板（兜底）** —— 律师无成型材料、或只想口述时启用。引擎按五轴
  逐项发问（最小必要集优先）；或给出一张**模板**（§8 附），律师一次填好贴回。

**【规则 · 工程编排】** 两形态**共用同一套五轴 schema 与同一套校验逻辑**：抽取 = 引擎自动填 schema，
引导 / 模板 = 人工填 schema。两条路填完都汇到同一步 —— **缺口确认**（§2）。不为两形态各造一套。
**五轴是"必须被登记的内容清单"，不是强制的提问 / 抽取顺序** —— 律师上传或口述时信息本就零散、乱序，
引擎按 schema 归位即可（如被告向预判诉请会先用到案由线索，则案由线索先登记，不受轴的排列所限）。

---

## 2. 最小必要集 vs 完整集（分级不拒跑的分界）

**【规则 · 起跑门槛】** 引擎起跑只需两样东西齐备：
1. **一笔可识别的、属于给付的争议给付** —— 我方主张的（原告向），或对方向我方主张 / 我方预判对方会
   主张的（被告向）那一笔。它须**含给付**、过边界守门（轴三第三步）；纯确认 / 形成 → 转派、不起跑。
2. **主张该给付一方的事实陈述**（轴二）—— 原告向 = 我方陈述；被告向 = 对方陈述（实有）或我方预判的
   对方陈述。**没有事实陈述，第一层原告站"假设陈述为真"就无对象可假设。**

*（理据 · 修正）* 旧版把"一个诉请"当门槛是错的：被告向、对方未上桌时，**诉请是引擎据事实与案由预判出来的
产物，不是律师的输入**。真正的输入原子是"**争议给付 + 主张方的事实陈述**"，诉请可由二者提炼或预判。

**【规则 · 立场是派生值，不是门槛】** 推演立场（原告向 / 被告向）**由我方地位派生**（§3 轴一），律师接案
时本就知道代理哪一方，几乎从不真的缺失，**不列为会阻断起跑的必填项**。仅当律师主动要求**双向**推演，
或我方为第三人（派生规则见轴一）时，才需显式设定。

**【规则】** 两样门槛之外（完整的当事人清单、金额精确、对方的完整陈述、案由定名、主体链细节、材料齐全、
时态附加登记）**全部是完整集**，缺则标 `【缺口】` 挂到对应轴，交后续阶段补 —— **越薄的接案卡，缺口旗标
越显著**，绝不假装齐全。

## 3. 五轴 schema（按律师接案动线排序）

### 轴一 · 当事人与我方地位（"谁告谁、我代理谁"）

**【规则 · 当事人】** 登记**当事人清单**（各方名称、地位、基本关系）。附两项旗标，**只标不挖**：
- **主体疑点旗标** —— 凡见挂靠 / 转包 / 违法分包 / 实际施工人 / 名实不符 / 主体适格存疑，标旗标，
  深挖留给阶段二与阶段三程序站（`engine/02` §2）。
- **管辖线索** —— 约定管辖 / 专属管辖 / 级别管辖的已知线索，标注待核。

*（理据）* 主体链与管辖是"裁定驳回起诉"和"主体适格落空"的高发处，接案卡只负责把它们**摆到引擎面前**，
真正的判断在程序站。接案卡过重，律师就不愿用。

**【规则 · 我方地位分两层填】**
- **本诉地位**（委托关系客观事实，互斥三选一）：**原告 / 被告 / 第三人**。这是我方的基础身份。
- **有无反诉**：无 / 有。**反诉是独立之诉**（`engine/01` §3.1），须单列。**我方在反诉中的地位由本诉
  地位镜像决定，不另填、也不得填成别的组合**：**本诉原告 ＝ 反诉被告；本诉被告 ＝ 反诉原告。**
  有反诉的，反诉作为独立之诉**单独走一套五轴与立场读数**。

**【规则 · 推演立场由地位派生，随"诉"而定】** 立场（研判读数方向）：**原告向 / 被告向 / 双向**。
- **原告 / 被告** → 直接派生对应立场；因本 skill 原告方、被告方都做，可独立设为**双向**（对手视角本就是
  己方预判的镜像，双向各跑一遍常常更值）。
- **第三人**（立场不能凭"第三人"三字派生，须再分）：**有独立请求权的第三人**——自己主张给付，读数近
  **原告向**；**无独立请求权的第三人**——依附于原告或被告一方辅助参加，读数**随其所辅助的一方**（辅助原告
  则原告向，辅助被告则被告向）。接案卡须据此把第三人落到一个具体立场。
- **本诉 + 反诉**：立场按诉分设，二者往往相反 —— 本诉原告在反诉中是反诉被告，故本诉走原告向、反诉走
  被告向（反之亦然）。同一委托人，两个诉，两套读数。

### 轴二 · 争议事实与双方主张（**全案的原料 · 关联分析法的入口**）

> 这一轴是引擎第一层能不能跑的根。关联分析法的原告站"假设原告陈述为真"、被告站"假设被告陈述为真"
> （`engine/02` §3），没有双方各自的事实陈述，两站都是空转。故接案卡必须把"各执何词"结构化下来。

**【规则 · 登记双方陈述，分栏并列】** 就争议给付所涉，分两栏登记事实陈述：
- **我方事实陈述** —— 我方（就该给付）主张的事实经过、关键时间点、依据的凭证线索。
- **对方事实陈述** —— 对方已作的陈述（有答辩 / 判决书时抽取）；**对方尚未上桌时，登记我方预判的对方
  说法**（会否认哪些事实、会主张哪些相反事实），标 `预判 · 待对方上桌校正`。这是"场景化跨越"在事实层
  的落点（`00-method` §3.2）。

**【规则 · 只登记，不裁断】** 本轴**只固定"谁说了什么"，绝不判谁真谁假、也不划争点**：
- **事实真伪** → 第二层证据站的活（`engine/02` §5）；
- **哪些是有效争点 / 哪些无争议** → 争点识别是 `engine/02` §4 的活。
接案卡只把双方陈述并排摆好，供引擎去比对、去识别不一致处。硬要在此判真伪或划争点，就越了界、且会污染
后面的中立研判。

**【规则 · 对齐给付、可留白】** 事实陈述**围绕轴三的每一笔给付组织**（哪段事实支撑 / 妨碍哪笔给付），
但材料薄时**允许只有我方一栏**（对方栏挂缺口）——第一层据我方陈述仍能跑有理性审查（分级不拒跑）。

### 轴三 · 诉的请求（识别 → 分类 → 边界守门 → 固定，一条龙 · **九步①的接案层落地**）

> 这一轴内部**必须按此顺序**：先认出诉请（可由轴二事实提炼 / 预判），才能分类；分类后才能守门；
> 过了门的给付诉请，才谈固定。顺序不可颠倒 —— 没识别就分类、没分类就固定，都是空转。

**【规则 · 第一步 识别每一项诉请】** 列出本案每一项诉请（承接轴二事实）。
- **原告向** —— 我方要主张的给付（判决前，诉请是我方自己的，本就清楚）。
- **被告向** —— 要固定的是**对方（原告）的诉请**：对方已起诉 → 从诉状抽取；**对方尚未起诉 / 诉状未见** →
  引擎据**轴二争议事实 + 案由线索**预判最可能的诉请群，标 `预判 · 待对方上桌校正`。

**【规则 · 第二步 分类】** 逐项判每一诉请属**给付 / 确认 / 形成**。

**【规则 · 第三步 边界守门】**（第一道闸，此刻才有诉请可守）：
- **给付之诉** → 进第四步固定。
- **纯确认 / 纯形成之诉**（确认合同效力、确认权属、撤销、解除、确权等）→ **标边界旗标 → 给转派建议
  （法律关系分析法）→ 该项不再往下跑**（`00-method` §5）。
- **混合诉**（一案含给付 + 确认 / 形成）→ **按请求逐项切分**：给付部分进第四步，确认 / 形成部分单独
  标边界。一项一判。

**【规则 · 第四步 固定】** 对**过了门的每一项给付诉请**，按类型登记要点（案由通用）：
- **给付金钱 / 实物** → 给付主体、种类、金额 / 数量、**构成及计算方法**；
- **请求履行行为** → 履行内容、方式、**是否便于执行**；
- **多被告担责** → 各被告责任**性质与份额**（连带 / 按份 / 补充）。
固定时若发现诉请**不明确 / 不正确 / 自相矛盾 / 疑遗漏可一并主张的请求**，按 §4 的律师版规则处理
（自纠 + 提示，无释明权）。

**【规则 · 诉请固定度另记一格】** 给整组诉请标一个**固定度**（清晰 / 有模糊 / 有矛盾 / 疑遗漏）。
它与材料成熟度、与事实陈述的完整度都不同轴（§5），不得混。

### 轴四 · 案由线索（**种子，非封顶，案由通用**）

**【规则】** 登记律师母语层的**民事案由线索**（如"建设工程施工合同纠纷""民间借贷纠纷"）—— 它是立案
关键，也是阶段四类案检索最强的过滤器，还被轴二 / 轴三的被告向预判用作依据（故可先行登记）。**但接案卡
只把它当线索登记，绝不当天花板**：下游找法（阶段二）仍跑完整检索顺序、跨法律关系检验竞合
（`00-method` §1.4 非封顶规则）。案由定不准也不停机 —— 标"案由待定"，引擎按争议给付实时推导兜底。

### 轴五 · 时态（引擎据此切前瞻 / 回溯）

**【规则】** 填一个开关：**有无一审判决书**。
- **无 → 前瞻**（一审判决前预判结果区间）。**主用途。**
- **有 → 回溯**（二审 / 再审：以已有判决为基准，预判改判 / 发回 / 维持）。回溯态**附加登记判决书原文
  内容**：原判**认定的关键事实**、**裁判主文**、当事人拟提的**上诉 / 再审事由**。
  —— **只登记判决书里有什么，不在此判"哪里是薄弱点"**：薄弱点识别是阶段四引擎回溯推演的活
  （`engine/03` §4 双时态），接案卡不做这个判断。颗粒度按材料而定，缺则挂旗标。

## 4. 律师版转译：固定 = 自纠 + 预判（无释明权）

**【规则 · 理据】** 九步①的"固定"在法官版靠**释明权**（法院释明、告知、记明笔录；原告拒绝确认法院
认定的法律关系又不明确的，裁定驳回起诉）。**律师没有释明权。** 故轴三第四步的"固定"，在律师版是两件
法官权力的替代动作：
- **自纠** —— 律师**自己**发现诉请不明确 / 不正确 / 矛盾 / 疑遗漏，当场向委托人问清、修正、剔除、提示补项
  （律师会见追问，非法官释明）。
- **预判** —— 预判**法官**会就哪一点释明、可能怎么认定法律关系。**这条真正展开在阶段二**（`engine/01`
  §2.3 定性风险）；接案卡只**标"此处法官可能释明 / 可能异议"旗标**，不展开。

**【规则 · 诉请充分性只提示、不终判】** 四项自纠里，唯"**疑遗漏可一并主张的请求**"这一项**依赖找法结果**
（要先有请求权基础，才知道有没有漏从权利，如利息 / 违约金 / 从权利）。故接案卡对"不充分"只作**前向引用**
挂着、只提示不锁定，等阶段二找法完成后回填 —— 接案卡不假装能独立判全诉请的充分性。

*（本节只给"为何这样固定"的理据；固定的四步操作在轴三，不在此重复。）*

## 5. 材料成熟度评级（与诉请固定度、事实完整度都不同轴）

**【规则】** 给整卷材料评一个成熟度级，它只决定**引擎第二层（证明前景）能到多深**，不决定诉请清不清楚、
也不决定事实陈述全不全：

| 级 | 材料状态 | 引擎第二层可达 |
|---|---|---|
| **L0** | 纯口述 / 一段话 | 只跑第一层（法律有理性）；第二层全标"证明前景待定 + 缺口" |
| **L1** | 关键文书（起诉状 / 合同等其一二；回溯态则为一审判决书） | 第二层就已有文书涉及的要件给初步前景，其余挂缺口 |
| **L2** | 部分卷宗（含部分证据） | 第二层对多数争议要件给前景，少数挂缺口 |
| **L3** | 完整卷宗（举证质证材料齐；回溯态含一审全案卷） | 第二层可给较实的证明前景 |

**【规则 · 三者分轴，补法各异】** 接案卡分开量三样东西，绝不压成一个"成熟度"：
- **诉请固定度**（诉请说清没有，轴三末）—— 低则回轴三自纠 / 提示；
- **事实陈述完整度**（双方各执之词齐不齐，轴二）—— 缺我方陈述则回轴二补；缺对方陈述则挂缺口 / 转预判；
- **材料成熟度**（证据全不全，本节 L0–L3）—— 低则标缺口、留待阶段五取证补强。
*（理据）* 三者是三回事：口述（材料薄）也能把诉请说清、把我方事实讲全；完整卷宗（材料厚）诉请也可能
自相矛盾、对方陈述也可能还没上桌。混作一谈，就会错判"这案子还缺什么"。

## 6. 产出与交接（handoff → engine/01）

交付 `engine/01-claim-and-defense.md` 一张结构化接案卡：
1. **轴一** 当事人清单 + 主体疑点旗标 + 管辖线索；本诉地位（原告 / 被告 / 第三人）+ 有无反诉（镜像、
   单列另跑）+ 推演立场（含第三人的派生结果；本诉与反诉按诉分设）；
2. **轴二** 争议事实与双方主张（我方陈述 + 对方陈述或预判，围绕各笔给付组织；只登记不裁断）+ 事实完整度；
3. **轴三** 逐项诉请（识别 → 分类 → 边界守门 → 固定）：边界旗标（转派项已标、混合诉已切分）、过门给付
   诉请的固定内容、自纠结果、被告向的预判诉请及"待校正"标记、**诉请固定度**；
4. **轴四** 案由线索（种子，标非封顶）；
5. **轴五** 时态（前瞻 / 回溯 + 回溯态判决书原文登记）；
6. **材料成熟度评级**（L0–L3）—— 与诉请固定度、事实完整度三轴分列；
7. **缺口旗标汇总** —— 哪些完整集字段缺、缺在哪轴、由后续哪阶段补。

## 7. 本文件不是什么

- **不含案由专属字段** —— 五轴对全部给付之诉通用；案由只作线索。建设工程不进接案卡结构。
- **不做法律推理** —— 不找请求权基础、不分要件、不判胜负。那是 `engine/01` 起的活。
- **不做事实认定、不识争点** —— 轴二只登记双方各执之词；判真伪是 `engine/02` §5，划争点是 `engine/02` §4。
- **不做定性** —— "法官会怎么认定法律关系"是阶段二定性风险；接案卡只标"此处可能有异议"旗标。
- **不预判回溯薄弱点** —— 回溯态只登记判决书原文；"原判哪里薄弱、能否改判"是阶段四引擎的活。
- **不深挖主体 / 管辖** —— 只做清单 + 疑点旗标；判断在程序站。
- **不放立场打法** —— 立场方向是读数参数，不是打法；打法在阶段六。
