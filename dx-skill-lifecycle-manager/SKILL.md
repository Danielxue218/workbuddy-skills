# DX 技能全生命周期管理器

## 概述

| 项目 | 内容 |
|------|------|
| **能力名称** | 技能全生命周期管理 |
| **核心功能** | 开源技能引入 → 去重判定 → 改名换姓 → 技能库归档 → 运行时部署 → 工作流映射 → 边用边改 → 月度汇报 |
| **输入要素** | 技能来源（文件夹路径 / GitHub URL / 市场技能名）、目标场景分类 |
| **输出成果** | 已改名的 DX 技能、更新的 STATUS.md、工作流映射记录、月度汇报文件 |
| **适用场景** | 每次引入新开源技能时；每月技能使用汇报；工作流梳理 |

## Phase 1：去重判定

**触发**：用户提供了新技能来源（文件夹路径 / GitHub URL / 市场技能名）。

### 步骤

1. **读取新技能的 SKILL.md**，提取以下字段：
   - `name`（技能名）
   - `description`（描述）
   - `tags`（标签）
   - 核心功能摘要（正文前 500 字）

2. **扫描运行时目录** `RUNTIME` 下所有已安装技能的 SKILL.md，逐一比对：
   - **名称相似度**：是否仅前缀不同（如 `case-retrieval` vs `dx-case-retrieval`）
   - **描述语义重叠度**：关键词重合 >= 60% 判为疑似重复
   - **功能范围重叠**：核心能力是否覆盖同一场景

3. **输出去重报告**：

```
┌─────────────────────────────────────────┐
│  去重判定报告                             │
├─────────────────────────────────────────┤
│  新技能：xxx                              │
│  判定结果：✅ 无重复 / ⚠️ 疑似重复         │
│  重复对象：（如有，列出技能名+重叠点）      │
│  建议：直接安装 / 合并 / 替换 / 跳过       │
└─────────────────────────────────────────┘
```

4. **若疑似重复**，向用户展示对比表，由用户决定：
   - **跳过**：不安装，记录到 STATUS.md 为 ⬜
   - **替换**：删除旧技能，安装新技能
   - **合并**：将新技能的有价值部分融入旧技能
   - **强制安装**：作为独立技能安装

## Phase 2：改名换姓（Rebrand）

**前提**：去重判定通过（无重复或用户决定安装）。

### 2.1 文件夹重命名

| 原名模式 | 新名模式 | 示例 |
|----------|----------|------|
| 无前缀 | `dx-` 前缀 | `case-retrieval` -> `dx-case-retrieval` |
| 其他前缀（mqc-、m17- 等） | 统一为 `dx-` 前缀 | `mqc-claim-basis` -> `dx-claim-basis` |
| 已有 `dx-` 前缀 | 保持不变 | `dx-evidence-evaluation` -> 不变 |

> **例外**：用户明确指定保留原名的技能不改（如 `guizang-social-card-skill`、`nano-banana-pro-image-gen` 等工具类技能）。

### 2.2 SKILL.md 元数据改造

对 SKILL.md 的 YAML frontmatter 执行以下修改：

| 字段 | 操作 | 示例 |
|------|------|------|
| `name` | 改为 `dx-*` 前缀的新名 | `name: case-retrieval` -> `name: dx-case-retrieval` |
| `author` | 统一改为 `DX` | `author: CSlawyer1985` -> `author: DX` |
| `version` | 保留原版本，首次改造附加 `-dx` 后缀 | `version: 1.0.0` -> `version: 1.0.0-dx` |
| `last_updated` | 改为当天日期 | `last_updated: 2026-07-27` |
| `source` | 新增，记录原始来源 | `source: github.com/CSlawyer1985/claude-for-legal-ZH` |
| `original_name` | 新增，记录原始技能名 | `original_name: case-retrieval` |
| `license` | 保留原许可证 | 不变 |
| `tags` | 追加 `DX改造` 标签 | 在现有 tags 后加 `DX改造` |

### 2.3 正文微调

- 在概述段落末尾追加一行：`> 本技能由 DX 基于开源版本改造，适配个人工作流。原始来源：{source}`
- **不改动**核心逻辑、步骤、方法论等内容——这些在 Phase 7「边用边改」中逐步调整

### 2.4 改名确认

向用户展示 before/after 对比表，确认后执行。格式见 `references/rebrand-conventions.md`。

## Phase 3：技能库归档

**前提**：Rebrand 完成。

### 3.1 场景分类

根据技能功能，归入 `SKILL_LIB` 下 16 个场景子目录之一：

| 编号 | 场景目录 | 适用技能 |
|------|----------|----------|
| 01 | 诉讼业务 | 诉讼全流程、证据、推理、裁判文书等 |
| 02 | 商事合同 | 合同起草、审查、履约风险等 |
| 03 | 公司法 | 公司治理、股权等 |
| 04 | 劳动法 | 劳动争议等 |
| 05 | 知识产权 | 商标、专利、著作权等 |
| 06 | AI治理 | AI 合规与治理 |
| 07 | 隐私合规 | 个人信息保护 |
| 08 | 产品法务 | 产品上线合规审查 |
| 09 | 监管合规 | 合规风险、监管监测等 |
| 10 | 法学院 | 法律写作反馈 |
| 11 | 法律诊所 | 法律咨询 |
| 12 | 法律团队协作 | 多角色协作 |
| 13 | Skill管理工具 | 技能管理本身 |
| 14 | 简报与社交 | 法律简报、朋友圈卡片 |
| 15 | 图片与设计 | 图片生成、Logo、PPT |
| 16 | 通用工具 | 通用辅助工具 |

> 无法确定时，询问用户归入哪个场景。

### 3.2 复制到技能库

```bash
cp -r {rebranded_skill_folder} "{SKILL_LIB}/{场景目录}/{dx-skill-name}/"
```

### 3.3 更新 STATUS.md

在 STATUS.md 对应场景的表格中追加一行：

```markdown
| {dx-skill-name} | ✅ | 开源改造 | {备注：原始来源简述} |
```

同时更新底部统计数字（已安装 ✅ 数量 +1，未安装 ⬜ 不变）。

## Phase 4：运行时部署

```bash
cp -r "{SKILL_LIB}/{场景目录}/{dx-skill-name}/" "{RUNTIME}/{dx-skill-name}/"
```

部署后验证：
- 确认 `{RUNTIME}/{dx-skill-name}/SKILL.md` 存在且可读
- 确认 YAML frontmatter 的 `name` 字段与文件夹名一致
- 确认 `disable` 字段不为 `true`（如为 true 需询问用户是否启用）

## Phase 5：工作流映射

### 5.1 数据文件

工作流-技能映射存储在 `WORKFLOW_MAP`（`workflow-skill-map.json`），结构如下：

```json
{
  "version": "1.0",
  "last_updated": "2026-07-27",
  "workflows": {
    "诉讼案件准备": {
      "description": "从接案到开庭前的完整准备流程",
      "skills": [
        "dx-claim-basis-nine-step",
        "dx-evidence-evaluation",
        "dx-case-retrieval",
        "dx-legal-article-retrieval"
      ],
      "phases": {
        "案件初筛": ["dx-claim-basis-nine-step"],
        "证据整理": ["dx-evidence-evaluation", "dx-evidence-argument-chain"],
        "法律检索": ["dx-case-retrieval", "dx-legal-article-retrieval"],
        "策略制定": ["dx-argument-chain-construction", "dx-argument-strength-evaluation"]
      },
      "created": "2026-07-27",
      "last_used": "",
      "usage_count": 0
    }
  },
  "skill_index": {
    "dx-claim-basis-nine-step": ["诉讼案件准备"],
    "dx-evidence-evaluation": ["诉讼案件准备"]
  },
  "monthly_reports": []
}
```

### 5.2 维护时机

| 时机 | 操作 |
|------|------|
| 新技能部署后 | 询问用户该技能属于哪些工作流，更新映射 |
| 用户使用技能时 | 记录使用情况，更新 `last_used` 和 `usage_count` |
| 用户梳理工作流时 | 按用户描述创建/更新工作流节点 |
| 月度汇报前 | 全量校验映射，清理失效引用 |

### 5.3 查询接口

用户可通过自然语言查询：
- "诉讼案件准备用到了哪些技能？" -> 列出该工作流下所有技能
- "dx-case-retrieval 属于哪些工作流？" -> 反查 skill_index
- "列出所有工作流" -> 输出工作流概览表

## Phase 6：月度汇报

### 6.1 触发方式

| 方式 | 说明 |
|------|------|
| 自动触发 | 每月 1 日 09:00 由 automation 自动执行 |
| 手动触发 | 用户说"生成技能月报"/"生成本月技能汇报" |

### 6.2 汇报内容

月报文件保存到 `REPORTS_DIR/{YYYY-MM}-skill-report.md`，包含以下章节：

1. **技能库概览**：总数、已安装数、未安装数、本月新增数
2. **本月变更记录**：新部署的技能、改名的技能、更新的技能
3. **工作流使用统计**：各工作流的 `usage_count`、`last_used`，按使用频率排序
4. **技能使用热度榜**：按 `skill_index` 中出现的工作流数量排序
5. **待处理事项**：疑似重复未决的技能、未归入工作流的游离技能
6. **下月建议**：基于使用数据给出的优化建议

### 6.3 模板

使用 `references/monthly-report-template.md` 作为输出模板。

## Phase 7：边用边改（Self-Evolving）

### 7.0 核心理念

技能不是一次写死的静态文件，而是随使用不断打磨的活文档。**每次调用本技能（或任何 DX 技能）时，执行者必须在同一回合内主动评估是否有改进空间，发现问题即刻修正，不等用户提醒，不延后处理。**

这是强制行为，不是建议。

### 7.1 自动修正触发矩阵

以下情况一旦发现，**无需询问用户，直接在本回合修改 SKILL.md**：

| 级别 | 触发条件 | 操作 | 示例 |
|------|----------|------|------|
| **P0 即时修** | 错别字、乱码、编码错误 | 直接修复 | `劥动法` → `劳动法` |
| **P0 即时修** | 引用了错误的工具名/命令名 | 修正为正确名称 | `search_file` → `Grep` |
| **P0 即时修** | 路径与实际不一致 | 修正路径 | 硬编码的旧路径 → 当前路径 |
| **P0 即时修** | YAML frontmatter 格式错误 | 修复格式 | 缺少 `---` 闭合 |
| **P1 确认后修** | 缺少必要的前置步骤 | 补充步骤并告知用户 | 安装前缺少安全审查步骤 |
| **P1 确认后修** | 触发条件不够明确导致误触发/不触发 | 优化 description 关键词 | 补充同义词 |
| **P1 确认后修** | 执行中发现更好的工作流或参数顺序 | 更新步骤描述 | 调整 Phase 执行顺序 |
| **P1 确认后修** | 技能输出格式与用户期望不符 | 调整输出模板 | 月报增加章节 |
| **P2 记录待办** | 发现潜在优化但当前不具备修改条件 | 记录到改进日志的"待优化"区 | 需要大量重写的逻辑 |

### 7.2 版本递增协议

每次修改 SKILL.md 后，根据修改幅度递增版本号：

| 修改类型 | 版本变化 | 示例 |
|----------|----------|------|
| 错别字/格式修复（不影响逻辑） | patch +1 | `1.0.0` → `1.0.1` |
| 补充步骤/优化描述（向后兼容） | minor +1 | `1.0.1` → `1.1.0` |
| 新增 Phase/重写核心逻辑 | major +1 | `1.1.0` → `2.0.0` |

同时更新 `last_updated` 为当天日期。

### 7.3 改进日志

每次改进后，在 SKILL.md 末尾的 `## 改进日志` 章节（如无则新增）追加记录：

```markdown
### v{版本号} - {YYYY-MM-DD}

- **触发场景**：{在做什么操作时发现了问题}
- **问题**：{发现了什么问题}
- **修正**：{做了什么修改}
- **级别**：P0 即时修 / P1 确认后修 / P2 记录待办
```

### 7.4 双写同步

修改 SKILL.md 后，必须同步到两个位置：

1. **技能库**（权威源）：`{SKILL_LIB}/{场景目录}/{dx-skill-name}/SKILL.md`
2. **运行时**（执行源）：`{RUNTIME}/{dx-skill-name}/SKILL.md`

```bash
# 技能库 → 运行时 同步
cp "{SKILL_LIB}/{场景目录}/{dx-skill-name}/SKILL.md" "{RUNTIME}/{dx-skill-name}/SKILL.md"
```

> 永远从技能库向运行时同步，不反向操作。

### 7.5 自我应用

本技能同样适用于自身。每次执行 dx-skill-lifecycle-manager 时，应自检：

1. 本技能的 Phase 1-6 步骤是否可执行、是否有遗漏
2. 路径约定是否与当前环境一致
3. 工作流映射数据是否需要更新
4. 月报模板是否需要调整
5. 改名规范是否覆盖了新遇到的前缀模式

发现问题后按 7.1-7.4 的流程自我修正。

### 7.6 改进原则

- **只改有问题的部分**，不做无意义的重写
- **保持向后兼容**，不删除已有字段（除非确认废弃）
- **及时记录**，每次改进都在当回合完成，不延后
- **不问用户**，P0 级别直接改，P1 级别改后告知
- **双写同步**，技能库和运行时保持一致

## 完整工作流串联

用户说"安装这个开源技能 {来源}"时，自动执行 Phase 1-5：

```
Phase 1 去重判定
  ├─ 无重复 → Phase 2
  └─ 疑似重复 → 用户决策 → Phase 2 / 终止
Phase 2 改名换姓
  ├─ 文件夹重命名
  ├─ SKILL.md 元数据改造
  └─ 用户确认 → Phase 3
Phase 3 技能库归档
  ├─ 场景分类
  ├─ 复制到技能库
  └─ 更新 STATUS.md → Phase 4
Phase 4 运行时部署
  ├─ 复制到 RUNTIME
  ├─ 验证
  └─ → Phase 5
Phase 5 工作流映射
  ├─ 询问用户归属工作流
  ├─ 更新 workflow-skill-map.json
  └─ 完成
```

Phase 6（月报）和 Phase 7（边用边改）是独立触发的，不依赖上述串联。

## 注意事项

1. **安全第一**：引入开源技能前，如包含可执行脚本（.ps1/.py/.sh），需先执行安全审查（参考 skills-security-check 技能）
2. **备份意识**：替换旧技能前，先将旧技能文件夹重命名为 `{name}.bak`，确认新技能正常后再删除
3. **编码安全**：所有文件操作使用 UTF-8 编码，Windows 路径含中文时注意引号包裹
4. **STATUS.md 同步**：每次增删技能后必须同步更新 STATUS.md，保持与实际部署一致
